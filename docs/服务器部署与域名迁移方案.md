# 仓库数据系统：服务器部署与域名迁移方案

版本：V1.0 · 日期：2026-09-30  
状态：部署准备方案；尚未执行 GitHub 发布、服务器安装、数据迁移或 DNS 修改。

## 1. 目标与部署边界

将现有库存与销售分析网页迁移到用户自己的腾讯云 Ubuntu 服务器。代码通过 GitHub 管理，服务器拉取经过验证的版本，使用独立子域名访问。服务器已承载其他项目，本项目必须使用独立目录、进程、数据文件和反向代理配置，与现有项目共存。

本阶段保留多仓库、自动获取 SKU、可购数量采集、历史快照、库存差额趋势、Excel 导出和采集记录。每天北京时间 08:00 的采集由服务器执行。入库在途和钉钉预警按后续阶段接入，不作为首次迁移的上线前提。

GitHub 负责保存代码和版本，腾讯云服务器负责运行应用、调用吉客云并保存数据，域名负责提供访问地址。GitHub Pages 静态托管不能代替本项目的后端和数据库。

## 3. 域名接入：新增子域名记录

此次需要增加的是 **DNS 解析记录**，不是在截图“修改 DNS 服务器”弹窗中增加或更换 NS。保留目前 Cloudflare 的两条 NS，在管理 `casebang.tech` 的 Cloudflare 账户中操作。[Cloudflare 管理 DNS 记录](https://developers.cloudflare.com/dns/manage-dns-records/how-to/create-dns-records/)

拟新增记录如下，正式创建前确认同名 A、AAAA、CNAME 及通配符影响：

```text
类型：A
名称：inventory
IPv4：139.199.63.119
TTL：Auto
代理状态：DNS only（仅 DNS，灰云）
完整域名：inventory.casebang.tech
```

为先验证国内直连链路，建议仅将这条新记录设为 DNS only。这样浏览器直接连接腾讯云公网地址；Cloudflare 只负责解析，不代理这条记录的网页流量，也不提供该流量的代理缓存/WAF 功能。不修改其他记录的代理状态。[Cloudflare 代理状态说明](https://developers.cloudflare.com/dns/proxy-status/)

保留 `@`、`www`、邮件记录及其他项目的记录；不新增未经配置的 AAAA 记录。一个公网 IP 可以承载多个子域名，由反向代理根据域名分别转发到不同本地端口。[Nginx 域名虚拟主机机制](https://nginx.org/en/docs/http/request_processing.html)

## 4. 目标运行结构

```text
用户浏览器
  └─ HTTPS inventory.casebang.tech
       └─ 现有反向代理（复用 80/443，新增本项目域名配置）
            └─ 本项目 Web 服务（拟 127.0.0.1:3108，先检查占用）
                 ├─ 登录、库存查询、Excel、任务状态
                 └─ 持久化数据库

服务器每天 08:00 定时器 / 网页手动采集
  └─ 创建持久化采集任务
       └─ 后台 worker → 吉客云官方 API → 快照与每日基准
```

迁移后吉客云请求由腾讯云服务器直接发起，不依赖 Codex 应用开机，也不依赖有人打开网页。浏览器到后端、后端到吉客云本身是正常的服务端架构；当前慢请求不能仅凭截图断定为“外网多转两层”。迁移后应分别测量吉客云耗时、数据库写入、页面返回和下载时间。

1 Mbps 带宽仍可能影响首次页面加载及大 Excel 下载；共享服务器的资源占用也需要实测。前端采用分页、静态资源缓存及压缩，数据库使用索引，采集采用受控并发，不能用提高并发无限提速。

## 5. 上线前必须完成的代码适配

### 5.1 生产运行时

当前源码使用 vinext、Cloudflare Workers、D1 和 Sites 登录。`package.json` 中的 `start` 实际调用 `wrangler dev --local`，属于本地模拟入口，不能直接作为 Ubuntu 正式部署方案。

迁移版本拟采用标准 Node.js 服务端运行方式，优先评估将现有页面/API 迁到标准 Next.js 生产构建；具体入口需完成兼容性验证后确定。当前源码要求 Node >=22.13.0，迁移时固定经过构建与依赖验证的受支持版本及锁文件。

需要替换 `cloudflare:workers` 环境读取、D1 数据库绑定、Sites 身份获取及平台专用构建/发布入口，产出真正的生产启动命令、健康检查接口和部署脚本。迁移改造完成前，不能把“GitHub 已有代码”视为“服务器可直接运行”。

### 5.2 登录与凭证

将 Sites/ChatGPT 身份替换为本项目登录或服务器已有的可信统一登录。首版可使用管理员创建账号的方式，不开放公共注册；迁移时显式映射旧 owner 到新用户，保持仓库和历史数据的归属隔离。

公开访问前验收登录、会话过期、退出、接口鉴权及跨用户隔离。反向代理须正确传递 Host 和协议信息，应用仅信任已知代理，核对同源校验及 HTTPS Cookie。

吉客云密钥只存在服务端配置中。沿用 `JACKYUN_APP_KEY`、`JACKYUN_APP_SECRET`；定时入口若保留则使用 `INVENTORY_CRON_SECRET`，并将 `INVENTORY_SITE_URL` 调整为新域名。钉钉四项配置仅在后续启用时设置。新登录所需的会话密钥由迁移实现定义，不复用其他项目密钥。

### 5.3 后台采集与明确状态

当前长采集仍与 HTTP 请求生命周期关联。迁移时要改为：点击采集后快速返回任务 ID，后台进程独立执行，前端轮询进度。关闭页面、刷新页面或代理请求超时，不应中断已经入队的任务。

- 任务持久化保存排队、运行、成功、部分成功、失败状态及开始/结束时间。
- 记录已处理 SKU、目录进度、库存批次、缺失条目、错误原因与心跳。
- 同一仓库只允许一个活跃任务；重复点击返回已有任务。
- 保存检查点，进程重启后可恢复或明确标记中断，不能永久显示“正在采集”。
- 失败批次有限重试并退避；缺失库存继续按用户已确认规则单独列出，不填为零。
- 完整发布规则和允许缺失的部分成功规则分开；写到一半的数据不能替换上一份可用快照。
- 前端收到非 JSON 错误时显示可理解的信息，并通过任务状态确认最终结果。

加大反向代理超时时间不能替代这些改造。多仓库共用受控调用并发，防止各仓库并行后累计请求超量。

### 5.4 数据库与云端定时

单机首版建议使用持久化 SQLite，评估 WAL、忙等待及写入事务；使用单个采集 worker 控制写入压力。必须检查 D1 SQL、批量事务和驱动行为的差异，完成回归后采用。若后续需要多实例或较高并发，再评估 PostgreSQL。

通过 systemd timer 每天 **Asia/Shanghai 08:00** 创建采集任务，后台 worker 消费任务。服务自启动，任务按仓库和日期幂等；离线错过时间后只补当前应采集的数据，并记录真实采集时间，不能伪造历史 08:00 快照。

保留“当天 08:00 后首次合格快照作为每日基准，后续手动采集更新当前库存”的规则。日期 D 的差额 = D 日基准库存 − D+1 日基准库存；仅连续日期且货品、单位可比时计算。该指标仍是库存差额，不等于真实销售订单数量，补货、调拨等会影响它。

## 6. GitHub 代码发布准备

建议建立独立私有仓库，候选名 `casebang-inventory`。以现有 `web-app` 为代码根目录，保留依赖锁文件、数据库迁移、测试和文档；仓库归属及名称待确认。

发布前检查工作区和 Git 历史，排除 `.env`、`.dev.vars`、私钥、真实接口响应、数据库、备份、日志及平台工具缓存。现有 `.gitignore` 已覆盖部分环境文件和构建目录，但仍须核查已跟踪文件；忽略规则不会自动移除曾提交的秘密。

仓库只放无真实密钥的配置示例。不要把项目外层的原始业务资料目录一并上传。服务器使用本仓库专用的只读 Deploy Key 拉取代码，不给服务器写仓库权限，不把访问令牌写进远程 URL。[GitHub Deploy Key 说明](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys)

每次上线记录提交 SHA/版本标签；服务器获取代码后部署指定版本，而不是在运行目录盲目 `git pull` 覆盖。国内服务器到 GitHub 的连通性需先测试；若不稳定，可以使用同一提交生成的构建包传输，不引入未知代码镜像。

## 7. 与已有项目共存

以下名称和路径为建议，必须先检查是否已存在：

- 服务用户：专用非 root 用户 `casebang-inventory`。
- 代码版本：`/opt/casebang-inventory/releases/<版本>`；`current` 指向当前版本。
- 持久化数据：`/var/lib/casebang-inventory/`，独立于代码发布目录。
- 服务端配置：`/etc/casebang-inventory/`，仅服务账户和管理员可读。
- Web 监听：`127.0.0.1:3108`；不直接开放到公网。
- 独立 Web、worker 和 timer 服务；日志设置保留期限及容量上限。

先查清当前 80/443 是由宿主机 Nginx、Caddy 还是容器代理占用。复用当前入口，不再启动一个抢占端口的代理，不覆盖全局配置、默认站点或现有项目配置。若已有成熟 Docker Compose 部署方式，可沿用并设置独立服务名、网络和数据卷；否则首版采用 systemd，最终依据现状决定。

新增精确匹配 `inventory.casebang.tech` 的站点配置，转发到已验证的本地端口。配置检查通过后平滑 reload，并回归现有项目。为新子域名申请受信任 HTTPS 证书并验证自动续期；不覆盖其他站点证书。安全组及防火墙保留现有规则，仅核对所需访问，不公开数据库或应用内部端口。

2 核 4 GiB 是共享资源，不预先保证余量。构建安排在低峰或独立构建环境；避免同时构建多个项目，运行资源限制由实测决定。

## 8. 服务器预检查清单

部署前先进行只读检查，以下是检查项目而非已执行结果：

```bash
cat /etc/os-release
free -h
df -h
ss -lntp
systemctl --type=service --state=running
systemctl list-timers --all
```

另核实 Docker/Compose 是否存在、反向代理站点和证书配置、现有域名对应端口、数据库备份方式、Node/Git 版本、GitHub 与吉客云连通性。代理完整配置可能含敏感信息，只在受控环境查看，不直接公开粘贴。检查结果形成部署前清单，记录已有项目访问结果供上线后对比。

## 9. 历史数据迁移

不能只迁代码或 Excel。须迁移数据库结构、迁移版本记录，以及至少以下全部业务表：`warehouses`、`sync_runs`、`stock_snapshots`、`stock_entries`、`daily_slots`、`alert_settings`、`stock_scopes`。实施时再扫描实际表结构，纳入新增表。

迁移步骤：

1. 先做一次只读导出和测试导入，验证字段、数值精度、外键及 owner 映射。
2. 正式切换时停止旧站新建采集并等待在途任务结束；若任务已中断，保留真实失败状态。
3. 做最终一致性导出，保留仓库、货品、SKU、数量、真实时间和每日基准关联。
4. 导入新数据库，逐仓库核对行数、快照数、成功状态、库存合计及每日基准日期。
5. 保留 staging/失败记录供审计，但不将其冒充成功快照；无合格基准的日期保持缺失。
6. 验证通过后开放新站写入，旧站保留只读核验期，避免两边同时更新。

原始导出和备份不进入 GitHub。SQLite 运行中采用一致性在线备份方式，不简单复制正在写入的单个数据库文件；上线前在独立位置验证一次恢复。

## 10. 实施阶段与交付物

### 阶段 A：环境盘点与运行时适配

确定子域名、端口、现有代理和服务器余量；完成 Node 生产运行、数据库适配、登录、持久化后台任务及定时入口。交付可本地生产启动的代码、测试、健康检查及配置示例。

### 阶段 B：GitHub 与服务器内网验证

清理并检查待发布内容，建立私有仓库；服务器配置只读拉取，部署指定版本到独立目录。先通过本地监听地址验证健康检查、登录、查询、一次完整采集和 Excel，暂不切换外部访问。

### 阶段 C：反向代理、域名和 HTTPS

备份现有代理配置；增加独立站点并核验其他站点正常。按证书验证方式安排 DNS 与签发顺序；在 Cloudflare 新增已确认的子域名记录，完成 HTTPS、重定向和续期测试。

### 阶段 D：数据切换与定时启用

最终迁移并核对历史数据。启用服务器每日 08:00 任务，验证无人打开网页时也能入库；前端仅在真实调度已启用后显示“云端定时已启用”。记录连续两日基准结果后核对销售差额列。

### 阶段 E：运行观察与回滚准备

保留上个代码版本、配置备份和迁移前数据库备份。应用异常优先回滚代码；若数据库结构不兼容，按专门的回滚方案处理，不能直接还原旧数据库丢掉上线后的新数据。数据恢复前先备份当前状态。

本项目回滚只涉及自己的进程、域名配置和数据；其他站点不随之重启或回退。旧 Site 若作为临时回退入口，必须明确其数据截止时间，避免被误认为最新数据。

## 11. 上线验收

- 原有项目的域名与接口保持可访问；新域名没有落入其他站点或默认站点。
- HTTPS、登录和接口权限有效；浏览器、日志、源码和下载文件不泄露密钥。
- 重启应用后仓库和历史数据仍存在；版本升级不清空数据。
- CK031 完整采集后数量、抽样可购库存、缺失列表与接口结果一致；CK007 的缺失条码记录明确可见。
- 采集过程中刷新/关闭浏览器不影响任务；前端能区分成功、部分成功、失败和仍在运行。
- 记录一次真实端到端采集耗时，分别记录外部 API 与数据库阶段耗时，不预先承诺固定秒数。
- 页面按 100 条起分页，排序覆盖全仓库，Excel 与当前筛选/导出定义一致。
- 每日 08:00 云端采集独立执行，同日重复触发不覆盖既定基准；连续日期差额可核对。
- 数据备份可恢复，升级和回滚演练不影响其他项目。
