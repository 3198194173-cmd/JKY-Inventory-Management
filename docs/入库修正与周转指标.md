## 计算口径

只有入库和消耗两种变动且库存口径一致时：

`期间消耗 = 期初库存 + 期间实际入库 - 期末库存`

等价于先从期末库存扣除期间入库，再与期初库存相减。库存差额为-499、实际入库500时，消耗为1；不是-999，也不能直接解释为销量0。

该公式应修正所有存在入库的日期，包括库存差额为正的日期。单有入库也无法排除调拨出库、采购退货、盘亏等其他消耗。

当前库存来源是`orderAbleQuantity`（可订购量），并非直接使用实物库存。实际入库单数量能否与可订购量增量一致，还必须结合锁定、订单、渠道预留等业务核验。不能接通一个入库接口后就声称得到了准确销售量。准确销售出库量宜从出库单按业务类型单独核对。

“销售量”为数量；“销售额”为金额。本次没有接入成交金额。

- `warehouseCode`：仓库编码；`goodsNo`：可选的货品编号。生产采集不传 goodsNo，获取仓库区间的全部入库。

## 已接入的采集与核算流程

1. 正常核验并保存全仓实时库存。入库查询期间，采集记录保持“采集中”；入库失败不会撤销已经保存的有效库存。
2. 按仓库及上次成功采集至本次采集的实际时间区间获取入库。固定每日基准另按其完整区间核算，避免中间手动采集截断每日数量；涉及手动快照的区间在详情单独显示，不重复计入每日销量及均值。
3. 使用 warehouseCode、inOutDateStart/End，不传 goodsNo，分页查询 erp-busiorder.goodsdocin.search。未归档与归档均查至明确空数组，以 recId 去重。权限、非JSON、冲突明细、重复页或分页不完整均不采用部分数据；防护上限2000页/归档状态，触发时明确失败。
4. 请求范围扩大至整秒，本地再按“入库时间 > 上次采集时间 且 <= 本次采集时间”精确过滤。服务器按货品编码汇总，不混加不同货品或单位的数量。同货品任一相关明细单位不匹配，只将该货品标记待核验。
5. 每个可比较货品均使用“期初库存 + 区间入库 − 期末库存”，不论库存下降、持平或增加。仓库完整查询成功且该货品没有入库记录时，才可认定入库0；查询失败时所有待核验货品保持为空，不冒充0。冲销合计为负时仍需核对；入库完整查询后计算结果为负时允许显示，按退货/回补计入净销量。
6. 以用户、仓库、货品及两个快照ID保存结果，记录查询范围版本 warehouse:v1。成功结果复用；失败、未解释及旧版单货品核验在下次采集重试。多个货品待核验时仍按区间共同查询，不逐货品请求。补查最近30天内已有连续每日基准；新货品缺少期初库存、缺日或单位变化不强行计算。
7. 详情展示原始差额、入库合计、采集区间、单号/类型/数量/时间及公式。每日销量、趋势、近7天均值、周转和Excel均使用相同核算结果；页面读取仅访问已保存数据库，不实时重查入库接口。
8. 原始库存、固定每日基准及后台单位均保留。新增0005、0006数据库迁移，Ubuntu启动自动应用；旧版仅查库存增加的结果需要重新核验全仓后才参与指标。

### 使用边界

本次已覆盖库存下降或持平时发生的入库。但尚未排除其他出库、退货、盘点和可订购量锁定变化，因此继续标为“消耗估算”。直接计算真实订单销量仍需销售出库及其他业务类型对账。

统计日期是上次基准的日期，窗口通常为08:00到次日08:00，首次历史手动基准可能在其他时间；不表示00:00到24:00自然日销量。查询采用入库单业务时间 inOutDate，详情另保留 gmtCreate；倒填业务日期、延迟过账、可订购量锁定变化及批量采集耗时仍可能产生边界差异，需要业务核对。

## 2026-10-09 在途、30天补货与组合编码处理

库存来源仍为 erp-stock.stock.skulist 的 orderAbleQuantity。erp.stockquantity.get 只用于发现本仓 SKU 并核验身份，不把目录的 currentQuantity / useQuantity 当成可购库存。按用户确认，带 + 的组合编码成功查询后没有返回可购库存时直接跳过，不补零、不列入未取得库存清单、不拦截预警。普通商品缺失、接口失败、权限或身份异常仍保留原检查。新口径从重新采集后生效，不改写历史库存。

每次仓库采集增加在途核验：erp.stockin.get 按仓库查询等待和部分入库申请，erp.stockin.get.v2 查询完整明细；显式查询申请日期从2020-01-01到采集开始时刻，避免接口默认近一个月漏掉旧申请。查询至空页，不采用返回的 total=0 作为结束条件。当前范围不包含2020年前的申请。

在途取明细 uninnerCount，并核对申请数量=已入库+未入库、明细合计=整单合计；部分入库保留未到数量。已知等待申请从列表消失后按单号查询全部状态，确认完成或关闭才退出在途。查询失败或数量矛盾显示待核验，不补零。已完成但实际入库尚未对账的申请继续复查。

实际入库按 billNo=申请单号关联既有 erp-busiorder.goodsdocin.search，并按仓库、商品、SKU、单位核对；这些记录只解释申请状态，不重复加到当前库存或销量修正。实际入库关联暂未对上时明确标注待核验。

补货数量=max(0,30×近7天未舍入销售均值－当前库存－在途)，四舍五入为整数；有负库存时保留负值参与计算。完整查询后无在途的商品按0计算；缺少有效均值或在途待核验时补货留空。主表新增在途、建议补货两列；点击在途数字查看商品申请单，顶部“在途记录”可查看全仓并按采集日期筛选。仅有在途、未取得库存的商品在记录和Excel中列出，其库存/补货留空。

历史自新版首次采集开始保存，日期选择器显示所选日最后一次采集的在途总量及当日完成记录，不推算尚未采集的过去状态。定时监测沿用每仓采集时间，手动采集也更新。新增0015迁移在启动时自动执行。
