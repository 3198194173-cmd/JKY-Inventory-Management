# 钉钉登录与账户独立仓库项目方案

日期：2026年10月15日。版本：V1.2 增加管理员仓库分享。适用系统：https://inventory.casebang.tech。

将现有单一账号登录升级为本公司钉钉登录。公司员工首次登录自动创建普通账户，每个账户拥有独立仓库配置、采集历史和预警记录；指定的本人钉钉身份作为系统管理员，可管理账号并查看、修改所有账户的业务数据。

已按先更新文档、再修改代码的顺序完成手机布局及钉钉账户隔离的本地实现；本轮不切换生产登录、不改现有账号密码。公司真实应用权限、登录凭证及扫码联调尚未完成，具体实现进度和上线条件见第十七节。

# 一 已确认的业务规则

1. 仅允许本公司钉钉成员登录，外部钉钉用户不能进入业务系统。

2. 本公司员工首次登录自动开通，无需管理员审批；新用户默认是普通成员。

3. 指定的本人钉钉账号作为管理员，增加“账户管理”入口。

4. 管理员可以查看和管理全部账户的数据与仓库配置。

5. 普通账户之间的数据、仓库列表和预警设置互相独立，不自动共享。

6. 现有库存、销售、在途和预警能力继续保留，本次不改变业务计算公式。

7. 当前共享 admin 账户的历史数据保留，迁移后归属指定管理员，不分发给新员工。

这里的“自动开通”不代表被禁用的账号可以通过再次登录自动恢复。管理员禁用具有优先级。

# 二 第一版范围与权限

## 普通成员

使用自己的钉钉身份登录，管理自己添加的仓库，设置采集时间、预警阈值、发送时间、名称排除条件和接收群；查看、采集和导出自己空间内的数据。接收群只能从该账号被授予使用权的企业群中选择。

普通成员不能列出其他账号、通过修改账户 ID 访问他人数据、给自己提权，或改变公司应用密钥。新账户默认没有仓库和历史快照，不自动复制管理员配置，不预选钉钉群，不自动发送消息；管理员可按第十八节主动提前分享仓库，接收人首次登录后沿用这份独立副本。

## 管理员

拥有普通成员能力，并可在“账户管理”中查看账户列表、角色、状态和最近登录时间；启用、禁用或归档账号；撤销会话；授予或撤销系统管理员角色；分配账号可用的预警群；进入指定账户的管理视图，查看和修改该账户的仓库、规则、任务及报告。

管理员操作他人空间时，页面持续显示“正在管理：某某账户”，所有相关 API 写入目标账户空间，审计同时记录实际操作者和目标账户。退出管理视图后回到自己的空间。

第一版仅设“系统管理员、普通成员”两类角色。角色变更须保证至少一名有效系统管理员；并发操作也不能绕过此限制。企业钉钉管理员身份不自动等于本系统管理员。

## 暂不实施

多公司入驻、部门共享空间、自定义复杂角色、员工间自动共享数据、账号间自动合并历史、每个用户自行填入企业应用密钥、面向外部客户开放登录。

# 三 钉钉登录与公司身份验证

## 登录方式

电脑浏览器提供钉钉扫码或官方授权登录入口；手机浏览器使用适用的官方授权流程。钉钉内打开网站时，联调企业 H5 应用免登能力。第一版需覆盖桌面浏览器、手机浏览器和钉钉内打开报告的主要路径，不能以桌面扫码成功代替移动端验收。

拟定回调地址：https://inventory.casebang.tech/api/auth/dingtalk/callback。正式首页和应用可见范围在企业钉钉开发者后台配置。

钉钉官方登录示例涉及应用配置、回调域名、取得用户身份后转换企业 userId，再查询用户详情；这也说明取得个人钉钉身份与完成企业成员验证是两个环节。[钉钉官方示例](https://github.com/open-dingtalk/h5app-out-login-demo/blob/main/README.md)

## 服务端认证顺序

1. 服务端创建一次性登录事务，生成随机 state，并绑定当前浏览器；建议五分钟过期、消费后立即失效。

2. 浏览器进入官方授权入口，服务端接收回调后校验 state、有效期和浏览器绑定。

3. 服务端使用授权码取得用户身份，密钥和令牌不交给前端。

4. 使用公司内部应用的企业权限，验证该身份属于配置的唯一公司，并处于允许使用应用的有效成员范围。

5. 企业验证成功后，按公司 corpId 与企业 userId 查找账号。没有账号则创建普通成员；已禁用或归档的账号拒绝登录。

6. 创建本系统会话。普通成员进入自己的空间；管理员默认也进入自己的空间，主动切换后才管理他人。

不相信浏览器传入的 corpId、姓名、手机号、邮箱后缀或角色。用户个人资料中的 unionId 也不能单独证明其属于本公司。外部联系人和上下游协作组织成员不因存在个人钉钉身份而被当作本公司员工。企业成员查询失败或权限不足时拒绝开通，不降级为“扫码成功即可登录”。

拟用官方能力为“获取用户 token、获取用户通讯录个人信息、根据 unionId 获取企业 userId、查询企业用户详情”。具体请求字段、返回状态及所需权限以开发时选定的官方接口与真实企业联调结果固定，不拼接不同年代的登录示例。参考：[获取用户 token](https://open.dingtalk.com/document/orgapp-server/obtain-user-token)、[个人信息](https://open.dingtalk.com/document/orgapp-server/dingtalk-retrieve-user-information)、[企业 userId 映射](https://open.dingtalk.com/document/orgapp-server/query-a-user-by-the-union-id)、[用户详情](https://open.dingtalk.com/document/orgapp-server/query-user-details)。

## 管理员首次绑定

部署前确定本公司的 corpId 和本人企业 userId，通过一次性管理员初始化过程绑定。必须经过真实企业身份验证，并记录绑定审计；不把“第一个扫码的人”设为管理员，不按姓名或手机号相似度匹配历史数据。初始化只能执行一次，后续管理员变更走受控管理流程。

# 五 配置与数据独立的具体边界

## 每个账户独立保存

- 仓库列表、仓库显示名称及账户自己的仓库配置。

- 每仓采集时间、采集开关、预警发送时间及自动预警开关。

- 销售均值阈值、库存周转阈值、排除商品名称关键词、选中的接收群。

- 库存快照、每日固定基准、销售日历、区间入库核验和历史单据关联。

- 在途快照、检测记录、等待及完成标记、建议补货结果。

- 采集任务与失败记录、预警报告、投递结果、导出记录。

例如，员工 A 与员工 B 都添加 CK031：A 修改预警规则、开始采集或调整时间，不改变 B 的配置；A 的历史快照和发送记录不能出现在 B 的查询中。管理员在 A 的管理视图修改配置，影响的是 A，不能误写到管理员自己的空间或 B 的空间。

同一个公司 ERP 仓库的真实库存本来相同。隔离的是本系统中的账户配置、采集归属和历史数据，不是把 ERP 里的同一库存变成两份不同实物。第一版不向 ERP 写库存；可查询仓库范围仍受公司服务端凭证权限限制。若需要额外限制“某员工只能查询某几个 ERP 仓库”，应再增加账户仓库授权名单，不能把配置隔离当成这种授权已经存在。

## 企业级基础资源

域名、HTTPS、公司 corpId、应用密钥、钉钉机器人凭证、吉客云凭证、公司可用群目录和服务端限流策略统一管理，不复制成每人一套密钥。普通成员看不到密钥；企业群目录与“账号获准选择哪些群”分别保存。

共享公司凭证不意味着共享业务查询结果。缓存键、快照归属、租约和去重键仍包含账户归属。

# 六 现有代码基础与必须补齐的地方

现状检查基于本地仓库代码，未把“已有 owner 字段”等同于已经实现多账户安全。

1. lib/local-session.ts 当前依赖一个环境变量账号和密码；所有登录会话写到固定 INVENTORY_OWNER_ID，缺少真实用户身份、账户状态和角色。

2. lib/auth.ts 的 currentOwner 从会话取得 owner，可作为改造入口，但管理员身份与目标数据空间必须分开表达。

3. warehouses、stock_snapshots、sync_runs、daily_slots 及多类核验、预警记录已有 owner 维度，适合继续用服务端数据归属进行隔离。

4. lib/inventory-store.ts 的 loadWarehouses 会自动补建默认 CK031。必须取消面向新账号的隐式建仓行为，并修改空仓库初始化路径，防止新员工首次打开就出现默认仓库或触发任务。

5. 库存明细通过 snapshot_id 归属快照，必须校验父快照所属账户；不能只按客户端提供的快照 ID 查询明细。

6. 后台任务已有 owner，但调度扫描目前并不验证多账户启用状态。每日采集、每小时在途检测和自动预警都要关联账户状态。

7. lib/alert-report-export.ts 当前按下载令牌和有效期读取报告，未要求当前登录者属于报告 owner；这是本次必须收紧的跨账户访问入口。

8. 群目录缓存已有 owner 与机器人应用维度，仍需补充账号可用群授权及统一入口校验。

9. 数据库真实结构应结合 drizzle 迁移与 lib/sqlite.mjs 运行时建表检查，不能只看 db/schema.ts 的静态定义就直接执行迁移。

现有销售均值、入库修正、在途核验、补货公式和历史基准规则不借本次账户改造重算或改写。

# 七 账户模型和授权上下文

## 账户

拟新增 accounts：内部 account_id、company_corp_id、dingtalk_user_id、必要的 union_id 与应用身份来源、显示名称和头像、角色、状态、唯一 data_owner、权限版本、企业身份最近核验时间、创建及最近登录时间。

唯一身份约束采用 company_corp_id 与 dingtalk_user_id；data_owner 也必须唯一。姓名、头像、手机号变化不改变账户 ID 和数据归属；更换企业应用或开发者主体时先核对身份映射，禁止自动合并账户。

## 会话和登录事务

新增账户会话表关联 account_id，保存令牌摘要、过期时间和权限版本；角色与状态由数据库判断，不相信前端或旧 Cookie 中的角色。新增登录事务表保存 state 摘要、浏览器绑定、过期及消费状态，防重放、重复回调和重复建号。

会话建议保持现有一天有效期。Cookie 使用 Secure、HttpOnly、SameSite=Lax，配合所有写操作的同源与 CSRF 校验，使钉钉授权回调和群内报告链接可以正常返回网站。退出、禁用、归档或权限变更均可撤销相关会话。

## 管理审计与群授权

新增审计记录，至少包含操作者 account_id、目标 account_id、动作、仓库编码或资源 ID、时间、结果和必要的变更摘要；不记录密码、授权码、accessToken 或密钥。读取他人空间及导出也要记录，不能只记录设置修改。

新增账号与允许接收群的授权关系；每仓实际勾选仍写入各账号自己的配置。新用户不会因机器人能看见某群就自动获得该群的发送权限。

## 服务端授权上下文

统一传递 actorAccountId、targetAccountId、dataOwner、role。普通接口只接受当前登录账户的 dataOwner；管理员接口先验证管理员角色，再解析被管理的 account_id。任何前端传来的 owner 字符串都不能直接作为可信归属。

后台任务与导出应同时保留数据归属和操作者身份。角色代表谁可以管理，不改变资料属于谁。

# 八 账号管理与页面改动

## 登录页

主入口改为“使用公司钉钉登录”，展示真实公司名称、扫码或授权状态及失败原因。对非公司成员、账号被禁用、应用不可用、授权过期分别给出清楚提示。切换上线完成后，公开页面不再提供旧共享密码入口。

## 个人工作区

导航显示姓名、头像、角色及退出入口。新用户进入空仓库引导，主动增加仓库后才建立自己的配置。页面继续采用当前极简浅色样式，库存字段与现有交互保持一致。 手机端采用第十五节的商品卡片布局，库存、销售均值、每日销量、周转、在途和补货清楚可见。

## 账户管理

管理员专用入口支持按姓名、企业 userId、角色、状态检索。详情展示账户状态、仓库列表、近期任务和预警记录。提供启用、禁用、归档、撤销会话、管理员角色调整、可用群配置与进入管理视图。

普通成员即使直接访问管理页面或构造管理 API，也必须被服务端拒绝。管理员不能查看他人的钉钉登录密码，本系统也不保存这类密码。

禁用不删除历史。恢复启用不自动恢复旧会话。归档默认保留数据，第一版不提供批量硬删除历史库存的按钮。

# 九 后台采集和预警的账户化

每日自动采集、每小时在途检测、自动预警均以“有效账户 + 自己启用的仓库配置”为目标。创建任务、领取任务、写入结果、投递消息前都重新校验账户状态；没有浏览器在线也可运行。

账户被禁用后，停止新增任务，取消尚未执行的队列；运行任务在安全检查点停止，不覆盖最后一份完整快照。已经发出的消息不能保证撤回；尚未发送的报告须在投递前检查状态。不能把“关闭网页”当成“停用账号”。

同一账号、同一仓库仍须防止重复采集或同一报告重复投递；租约、限流计数、幂等键和错误重试都带数据归属。两个用户设置相同仓库时，各自的任务不能覆盖对方，也不能用全局仓库去重误吞其中一个用户的更新。

第一版沿用单个 worker 与全局外部接口限流，增加按账户公平排队，避免一个账号占满全部采集资源。暂不共享历史快照来节省调用。真实账户数、仓库数与采集耗时明确后，再决定是否增加只读源数据缓存；这种优化必须另行证明不破坏隔离。

新员工自动开通不会自动获得管理员历史群设置，也不会立即群发预警。不同账户若有意对同一群发送报告，应在卡片中显示报告所属账户，避免来源不清。

# 十 报告和导出的访问规则

网页库存导出、预警导出、销售明细及在途单据都必须先验证当前会话，再校验目标数据归属。

第一版将钉钉报告下载改为“报告所属账户本人或系统管理员可下载”。登录后仍校验报告所属账户，不因为持有链接或属于本公司就允许查看他人的报告；登录往返只允许本站受控相对路径，防止开放重定向。

原有下载令牌只作报告定位和随机访问凭证的一部分，不能绕过账户权限。已有报告记录中的 owner 可用于回溯授权；过期令牌继续失效，不为旧公开链接保留匿名例外。

这会带来一个明确变化：同群普通成员如果不是报告所属账户，第一版不能直接下载该账户的 Excel。若后续需要群内协作下载，可增加有记录的“向指定公司成员共享报告”功能，不默认开放全公司数据。

钉钉卡片内容本身是用户主动向获准群发送的副本，群成员能看到其内容；网站的数据隔离不会撤回他人已读、已保存的消息或文件。管理员配置可用群时应据此选择发送范围。

# 十一 老数据迁移与恢复

## 迁移原则

优先保留现有 owner 值，不批量改写库存历史。先把旧 INVENTORY_OWNER_ID 对应的数据归属绑定给经验证的本人管理员账户；不能仅凭默认字符串 admin 推定真实身份。

新员工生成全新的 data_owner。员工与管理员添加同名仓库也不继承旧快照、销售基准、在途或预警发送结果。

## 实施顺序

1. 使用 SQLite 在线备份或停写后的完整一致性备份，避免只复制主数据库而遗漏 WAL；同时备份环境变量与代码版本，记录业务表行数和关键关联。

2. 暂停调度并确认没有在运行的采集及投递任务，再做数据库升级，避免边迁移边写入。

3. 以新增表和可回退字段为主建立账户、会话、身份绑定和审计结构，保留旧业务 owner 与主外键。

4. 完成指定管理员的真实钉钉身份绑定与旧数据归属映射。检查旧管理员仓库、近7天销售、日历、在途和发送历史均能查看。

5. 用两个普通测试员工验证互不可见，且不会被隐式创建 CK031；测试管理员有明确目标上下文的管理权限。

6. 关闭公开共享密码入口，撤销旧共享登录会话；启用钉钉登录后恢复调度。

7. 对比迁移前后表行数、每日基准及关键业务结果，观察任务与投递记录。

## 恢复与回退

上线保留独立维护通道，可经服务器命令行恢复本公司有效管理员绑定，不公开一个绕过企业校验的共享密码入口。

数据库迁移后若已有新写入，不能直接覆盖成旧备份而丢掉新数据。优先关闭新登录和新任务、保留业务记录并执行兼容性回退；只有停止写入、导出差异并确认恢复范围后才使用全量恢复。

后续改名、换头像或角色调整不改变 data_owner。将数据迁给另一个人属于独立管理操作，第一版不自动执行。

# 十三 验收用例

1. 本公司新员工首次登录自动创建且只创建一个普通账户；重复回调、并发扫码不产生重复空间。

3. 预先指定的本人身份成为管理员；其他员工、同名员工或第一个扫码者不会因此得到管理员。

4. 员工 A、B 同时配置 CK031，分别设置不同时间、阈值、名称过滤和接收群，互不修改。

# 十五 手机端布局与交互

2026年10月15日补充。先将本节写入方案，再开始手机布局代码；账户登录与隔离仍按前述阶段实施。

## 问题与目标

当前手机沿用电脑版宽表，固定商品列占据大部分屏幕，需要左右反复拖动才能看到库存与其他字段；手指滑动时，行内趋势图还可能误弹悬停提示。手机端应优先让用户完整阅读一件商品，不通过缩小字号强行塞入全部表格列。

宽度不超过760像素时使用商品卡片列表；大于760像素继续使用现有桌面表格。手机主体纵向滚动，不设置遮挡数据的固定商品列或另一个内层纵向滚动区。

## 商品卡片的字段顺序

1. 顶部显示商品编码、完整名称和等待入库或入库完成标记，编码和长名称允许换行，不只靠悬停查看。

2. 当前库存单独突出展示，附带原始库存单位；旁边提供“趋势与日历”入口。

3. 下方使用两列指标区：第一行“销售均值、库存周转”，第二行“在途数量、建议补货 / 30天”。每个数字都有常驻字段名，单位与未知状态可见。

4. 每日销量在同一商品卡片下方按日期小格展示，默认展示最新7个日期；选择14或30天时，可展开同一商品的其余日期。日期、销量、负数、未知和入库标记不省略。

5. 点某个日期直接打开已有销量日历并选中该日，查看库存计算和入库单据；点在途数量打开该商品的申请单与在途记录。

补货公式保持为“30×未舍入销售均值−当前库存−在途数量”，最终四舍五入、最低0。0显示“无需补货”；未知和不满足计算条件显示说明，不伪装成0。销售均值仍取近7个完整日期，显示14或30天不改变均值口径。

## 查询与操作

保留仓库选择、商品搜索、库存排序、日期范围、导出、采集和分页；增加手机可直接使用的“按某日销量排序”和升降序操作，不依赖已隐藏的桌面日期表头。

手机上的指标说明改为可点击展开，明确库存来源、销售均值、每日销量、库存周转、在途和补货口径，不能只依赖鼠标悬停。等待入库保留淡黄标记，入库完成保留淡绿标记及原24小时规则，库存预警仍按本仓规则标红。

顶部筛选区适当收紧留白，触摸按钮保持容易点击；输入框采用适合手机的字号，减少iOS输入时自动放大。使用自然页面滚动及底部安全区域，避免按钮或数据被遮挡。

## 性能与一致性

手机和电脑使用同一个库存接口、同一份查询条件与字段计算结果。响应式切换只改变排版，不创建新的采集、不发送预警、不复制数据。

每页仍遵守原分页条数，但手机先展示20件商品，提供“继续显示本页商品”和明确的已展示数量；不能让用户误以为只采集了20件。本页统计仍对应服务器返回的整页结果，不是当前已展开的20件。

手机列表默认不挂载每件商品的交互折线图，避免数百张图造成卡顿或阻碍纵向滑动。需要趋势时进入详情查看。加载更多商品、切换排序和展开日期不丢失或重算库存数据。

## 实施边界

本轮先完成不依赖钉钉应用新权限的手机布局代码及必要的详情日期定位。钉钉登录、管理员绑定、账户隔离和生产登录切换需要完成公司身份与应用权限准备后，继续按项目阶段实施。

## 操作流程

管理员在“账户管理 → 仓库分享”输入公司同事手机号，服务端查询本企业通讯录并展示姓名、userId 和掩码手机号；也可以选择已有公司账户。确认接收人后，选择管理员本人仓库并点击“确认复制”。即使当前正在管理其他账户，分享来源仍为实际管理员自己的空间。

未登录同事在确认复制时才创建独立账户，显示“待首次登录”。首次真实钉钉登录按 CorpID + userId 找到该账户，并核验 unionId，沿用已复制的数据，不重复开通账户；首次登录前不执行后台采集。

## 复制范围与独立性

一次性复制所选仓库配置、所有已完成库存快照、每日基准、销售/入库核验、在途历史和完成标记、已结束采集记录。快照重新分配 ID，并同步重映射历史关联；数量精度、缺失状态和原时间保留。完成标记不重新开始24小时计时。复制后两人分别采集、修改和保存历史，不持续同步。

目标已有同编码仓库时跳过，不覆盖、不合并。复制预警规则和时间，但自动预警关闭；群授权、已选接收群、发送记录、报告下载令牌、会话及运行中任务不复制，也不主动通知同事。

## 权限、可靠性与上线条件

手机号查询只允许有效管理员，限制查询频率，原始手机号不写入数据库、URL、审计或日志。身份凭证10分钟有效并绑定管理员；确认复制前再次在线核验成员身份，禁用、归档、离职或身份不一致均拒绝。创建账户、复制多仓库和保存幂等结果在同一事务内完成，失败全部回滚；审计记录实际操作者、接收人和复制/跳过清单。

同一个钉钉应用需增加“根据手机号姓名获取成员信息的接口访问权限”（qyapi_get_member_by_mobile），保留成员信息读权限及覆盖接收人的通讯录范围，并发布新版本。个人手机号信息权限不能替代按手机号查找企业成员。采用 topapi/v2/user/getbymobile → topapi/v2/user/get 核验，不按姓名猜测身份。参考：[钉钉手机号查询接口](https://open.dingtalk.com/document/orgapp/query-users-by-phone-number)。
